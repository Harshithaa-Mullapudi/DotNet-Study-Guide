01. Database Fundamentals

Database, tables, SQL basics, DBMS and RDBMS.

Core terms

  • Database: organized collection of data that can be stored, queried, updated and managed.
  • Table: related data arranged in rows and columns.
  • Row/record: one stored instance, such as one student.
  • Column/field: one attribute, such as Name or Age.
  • Schema: the structure that defines tables, columns, types, keys, constraints and relationships.
  • Primary key (PK): uniquely identifies a row. A PK must be unique and non-null.
  • Foreign key (FK): references a key in another table and helps enforce referential integrity.

SQL fundamentals

OperationPurposeExample
SELECTRead dataSELECT * FROM Student;
INSERTAdd rowsINSERT INTO Student (Name) VALUES ('Asha');
UPDATEChange existing rowsUPDATE Student SET Age = 22 WHERE Id = 1;
DELETERemove rowsDELETE FROM Student WHERE Id = 1;
  • WHERE filters rows; always check the predicate before UPDATE or DELETE.
  • ORDER BY sorts results; GROUP BY groups rows for aggregate calculations.
  • Common aggregates: COUNT, SUM, AVG, MIN, MAX.
  • DBMS: software to create, query, secure and manage databases.
  • RDBMS: a DBMS based on relational tables, keys, constraints and relationships. PostgreSQL is an RDBMS.

02. PostgreSQL

Relational database, architecture, transactions, concurrency, reliability and .NET connectivity.

  • PostgreSQL: open-source object-relational database system with SQL support, constraints, indexes, transactions and extensibility.
  • Architecture: client/application connects to the PostgreSQL server; the server processes SQL, accesses data and returns results. PostgreSQL uses processes and shared resources to handle connections and work.
  • SQL support: queries, joins, aggregates, constraints, views, transactions and advanced database features.
  • Transactions / ACID: Atomicity (all or nothing), Consistency (valid state), Isolation (concurrent work is controlled), Durability (committed work persists).
  • Concurrency: PostgreSQL uses MVCC (multi-version concurrency control) so concurrent readers and writers can often proceed without blocking one another unnecessarily. Locks still exist.
  • Scalability: suitable indexing, query tuning, connection management, partitioning, replication and infrastructure choices support growth.
  • Reliability: write-ahead logging (WAL), backups, recovery and replication options support durability and availability; these must be configured and tested.
  • Cross-platform: runs on major operating systems and supports many client languages.
  • PostgreSQL + .NET: Npgsql is the .NET data provider; Npgsql.EntityFrameworkCore.PostgreSQL integrates PostgreSQL with EF Core.

Connection string parts

FieldMeaning
HostServer name or address
PortPostgreSQL listening port (often 5432)
DatabaseTarget database name
Username / PasswordCredentials used to authenticate
Keep credentials out of source control. Use development secrets or environment-specific configuration, and restrict database permissions.

03. ORM Fundamentals

Object-relational mapping: translating between C# objects and relational data.

  • ORM: maps object-oriented code to relational tables and columns.
  • Object-to-table mapping: a C# entity type maps to a table or other database object; properties map to columns; relationships map to keys and navigation properties.
  • Automatic SQL: an ORM can translate supported LINQ expressions into SQL and map returned rows to objects.
  • Typical workflow: create/query an entity → ORM tracks or materializes it → changes are saved → provider executes database commands.
  • Advantages: less repetitive SQL, productivity, compile-time typing for many queries, maintainability and centralized mapping.
  • Limitations: query translation has limits, generated SQL may be inefficient, abstraction can hide database behavior, and complex reports may need carefully written SQL.
  • Performance: understand generated SQL, avoid loading unnecessary columns/rows, watch for N+1 queries and excessive tracking.
  • Raw SQL: useful for provider-specific or complex operations, but parameterize values and avoid unsafe string concatenation.

04. Entity Framework Core (EF Core)

The .NET ORM and its architecture.

  • EF Core: Microsoft's cross-platform ORM for .NET; it maps entity classes to database structures and supports LINQ queries and change tracking.
  • Provider model: a database provider translates EF Core operations into database-specific SQL and communicates with the database driver.
  • DbContext: session-like unit for querying, tracking and saving entities.
  • DbSet<T>: access point for querying and operating on a particular entity type.
  • Change Tracker: records entity states and property changes for persistence.
  • LINQ query processing: EF Core builds a query expression, translates supported parts into SQL, executes it through the provider, and materializes results.
  • Request flow: API/controller → application/data layer → DbContext → EF provider/Npgsql → PostgreSQL → results back through the application.
  • Benefits: LINQ, tracking, migrations, relationships, multiple providers and reduced repetitive SQL.
  • Limitations: provider differences, translation limitations, tracking overhead, and need to inspect SQL for performance-sensitive queries.

Answer: Change Tracker, which works as part of DbContext.

05. EF Core Development Approaches

Code First, Database First and Model First.

Code FirstDefine entity classes and model configuration in C#. Use migrations to create or update the database schema. Useful when the application team owns schema evolution.
Database FirstStart with an existing database. Scaffold entity classes and DbContext from its schema. Useful when the database already exists or is managed externally.
Model FirstHistorically, EF6 supported a visual EDMX model-first workflow. EF Core does not provide the same built-in classic EDMX Model First designer workflow.

Typical workflows

  1. Code First: define entities/configuration → create migration → inspect migration → update database.
  2. Database First: design or connect to database → scaffold → review generated entities/context → use in application.
  3. Model First conceptually: design a model then generate a schema; for EF Core, similar goals need other design tools or a code-first workflow.

Trade-offs

  • Code First offers application-controlled schema changes and migration history, but model and database must stay synchronized.
  • Database First reflects the real schema, but re-scaffolding and custom-code separation must be managed.
  • Choose based on who owns the schema, whether it already exists, and team deployment practices.

06. DbContext

Query execution, entity management, saving, lifecycle, dependency injection and disposal.

  • Purpose: coordinates queries, entity tracking and persistence; behaves like a short-lived session/unit of work.
  • Entity management: tracks entities returned by tracking queries and entities attached or added by application code.
  • Query execution: LINQ queries are composed first; terminal operations such as ToListAsync() execute them. EF translates supported expressions and materializes results.
  • Saving: SaveChanges()/SaveChangesAsync() detects changes and asks the provider to persist inserts, updates and deletes.
  • Lifecycle: DbContext is not thread-safe. Use a short-lived instance, commonly one scoped instance per web request; dispose it when done.
  • Dependency Injection: AddDbContext<TContext>() registers a scoped context by default in ASP.NET Core. Configure its provider and connection through options.
  • Change detection: EF Core compares tracked values/snapshots or uses configured notifications to determine changes.
  • Tracking vs no-tracking: tracked queries support updates through the context; AsNoTracking() can reduce overhead for read-only results.
  • Async: use asynchronous database operations in web apps to avoid blocking request threads while waiting for I/O. Do not run concurrent operations on the same DbContext.
// Conceptual registration
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(connectionString));

07. DbSet<T>

Entity collections, querying and state-changing methods.

  • DbSet<Student> or DbSet<Employee> represents the set of an entity type in the EF Core model and is used to query and operate on it.
  • Querying: compose LINQ using methods such as Where(), OrderBy(), Select() and terminal operators such as ToListAsync().
  • Changes: Add() marks an entity Added; Update() attaches/marks an entity for update; Remove() marks it Deleted. These usually stage state rather than immediately executing SQL.
  • DbContext interaction: DbSet operations coordinate with the context's Change Tracker; the context discovers/configures entity types through its model.
  • Deferred execution: query composition alone generally does not execute SQL; enumeration or terminal operations do.
  • Persistence: call SaveChanges/SaveChangesAsync to persist pending changes.

08. Change Tracker

Entity states, original/current values, snapshots, detection and SaveChanges workflow.

StateMeaningTypical example
DetachedNot tracked by this contextNew object not attached
AddedWill be inserted on saveAfter Add()
UnchangedTracked, no detected changesFresh tracked query result
ModifiedOne or more properties changed/markedTracked property updated
DeletedWill be deleted on saveAfter Remove()
  • EF Core retains original and current values for tracked properties; snapshot tracking can compare them to detect changes.
  • Changes can be detected automatically during SaveChanges, or explicitly via change-detection APIs.
  • Typical lifecycle: query/attach/add → state tracking → change properties → detect changes → SaveChanges → database commands → states normally become Unchanged after successful save (deleted entries are detached).
  • Inspect with context.Entry(entity).State and context.ChangeTracker.Entries().
  • AsNoTracking() avoids tracking for read-only queries, but those results are not automatically tracked for later updates.

09. EF Core Configuration

DbContextOptions, provider, connection strings, logging, tracking, DI and packages.

  • DbContextOptions: holds configuration such as provider, connection, logging and context behavior.
  • DbContextOptions<TContext>: typed options supplied to the context constructor; the context commonly passes them to base(options).
  • Provider: configure PostgreSQL with UseNpgsql(); another provider would use its own extension.
  • Connection string: Host, Port, Database, Username and Password identify the connection. Store secrets securely and vary configuration by environment.
  • Logging: EF Core logging can expose generated SQL and database activity; avoid leaking sensitive values in logs.
  • Tracking behavior: can be configured for a context, and individual queries can use AsNoTracking().
  • DI: AddDbContext<TContext>() commonly registers the context as scoped. Inject it rather than manually constructing it in controllers.
  • Packages: EF Core runtime, provider, design-time package/tooling and Npgsql driver/provider must be compatible versions.
  • Design-time vs runtime: runtime configuration serves the running app; design-time tooling must also be able to create/configure the context for migrations or scaffolding.

10. EF Core Model Building

Model metadata, entity/property discovery, ModelBuilder, OnModelCreating and caching.

  • EF model: metadata describing entity types, properties, keys, indexes, relationships, mappings and constraints.
  • Discovery: EF Core discovers entity types through DbSet properties, navigation properties and explicit configuration. Property conventions infer types and relationships where possible.
  • Metadata: EF Core builds a model from conventions, attributes and Fluent API, then uses it to translate queries and persist changes.
  • Model caching: the model is typically built once per context model configuration and cached to avoid rebuilding for every query.
  • ModelBuilder: the API used to configure entities and their mapping.
  • OnModelCreating(ModelBuilder): override in DbContext to add model configuration.
  • Entity<T>(): selects an entity for configuration, for example modelBuilder.Entity<Employee>().
  • Fluent API: configures columns, keys, indexes, relationships and other details in code.

11. EF Core Migrations

Schema synchronization, migration files, commands, history, applying and rollback.

  • Purpose: record incremental schema changes so a database can be updated as the model evolves.
  • Workflow: change model → add migration → inspect generated operations → apply migration to database.
  • Initial migration: creates schema operations for the current model. Use a meaningful migration name.
  • Migration class: contains Up() operations to apply changes and Down() operations to reverse them where possible.
  • Designer file: stores migration metadata/target model information used by tooling. The exact generated file arrangement depends on EF Core tooling.
  • Model snapshot: records the current model used to compare later changes when generating migrations.
  • Partial migrations: generated migration classes may be partial; normally inspect generated operations rather than casually editing them.
  • History table: __EFMigrationsHistory records applied migrations, commonly with migration ID and product version.
  • Commands: dotnet ef migrations add Name, dotnet ef database update, dotnet ef database update MigrationName, dotnet ef migrations remove, dotnet ef migrations list, dotnet ef migrations script, dotnet ef database drop.
  • MigrationBuilder: supplies operations such as create/drop table, add/drop column, add foreign key and create index; provider generates provider-specific SQL.
  • Apply/rollback: updating to a target migration applies or reverts migrations in the chain. Rollbacks can lose data, so review before production use.
  • Scripts: SQL scripts can be reviewed and deployed through controlled release processes.
  • Design time: tooling must construct the DbContext to discover the model and generate migrations; design-time services/configuration are separate from normal request execution.
Safety: do not treat migrations as a substitute for backups or production deployment review. Inspect generated SQL, test migrations and plan for existing data.

12. EF Core Configuration Approaches

Conventions, data annotations, Fluent API and precedence.

ConventionsEF Core's default rules infer common keys, relationships and column mappings. Least explicit, minimal code.
Data annotationsAttributes on entity properties/classes, such as [Key], [Required], [MaxLength(100)], [StringLength], [Table], [Column] and [ForeignKey].
Fluent APICentral configuration in OnModelCreating() using methods such as HasKey, Property, IsRequired, HasMaxLength and relationship methods.
  • Typical precedence: explicit Fluent API overrides data annotations, which override conventions for the same configuration.
  • Use conventions for standard cases; annotations for simple model-local rules; Fluent API for advanced or centralized configuration.
  • Keep configurations readable and avoid contradictory rules across approaches.

13. Entity Relationships

Normalization, keys, cardinality, principal/dependent and integrity.

  • Why relationships: connect related data while avoiding unnecessary duplication.
  • Normalization: store each fact in an appropriate place to reduce redundancy and update anomalies. For example, store Department details once rather than repeating the department name on every employee row.
  • One-to-one: one principal row relates to at most one dependent row, and vice versa according to the model.
  • One-to-many: one Department can relate to many Employees; the FK is commonly on Employee, the many/dependent side.
  • Many-to-many: many students can join many courses; typically represented by a join table/entity with two foreign keys.
  • PK/FK: primary keys identify rows; foreign keys reference principal keys.
  • Referential integrity: foreign-key constraints prevent references to nonexistent principal rows.
  • Principal/dependent: the principal is the referenced side; the dependent holds the FK in typical relationships.
  • Discovery: EF Core considers navigation properties, FK naming, keys, conventions and explicit metadata/configuration.

14. Navigation Properties

Reference and collection navigations, initialization and nullability.

  • Reference navigation: points to one related entity, such as Employee.Department or Employee.PayrollAccount.
  • Collection navigation: represents multiple related entities, such as Department.Employees, often typed as List<Employee> or ICollection<Employee>.
  • Inverse navigations: Employee.Department and Department.Employees represent opposite sides of the relationship.
  • Collection initialization: initializing with new List<Employee>() prevents a newly created entity's collection from being null.
  • Null-forgiving operator: null! suppresses a nullable-reference warning; it does not create an object or guarantee that EF has loaded a navigation.
  • Nullable reference types: use nullable types when absence is valid, and configure required/optional relationships consistently.
  • Loading: navigation properties do not automatically load related data just because they are declared; use Include/eager loading or other configured loading approaches.
// Conceptual navigation properties
public Department? Department { get; set; }
public ICollection<Employee> Employees { get; set; }
    = new List<Employee>();

15. Relationship Discovery & Delete Behaviors

Conventions, metadata, foreign keys and delete rules.

  • EF Core discovers relationships from navigation properties, primary keys, FK properties with conventional names (such as DepartmentId), and explicit configuration.
  • When conventions cannot infer the intended relationship, configure it with Fluent API or suitable attributes.
  • Cascade: deleting a principal can delete dependents, depending on relationship and database behavior.
  • Restrict: prevents principal deletion when dependent rows reference it, where enforced by the provider/database.
  • SetNull: sets the FK to null; the FK must be nullable and database/provider configuration must support it.
  • NoAction: does not configure cascading action; exact constraint behavior depends on provider/database.
  • Delete behavior must reflect business rules and referential integrity, not just convenience. Payroll/audit records may need retention.

16. One-to-Many Relationship

Department → Employees, FK configuration and migrations.

  • One Department can have many Employees; each Employee typically belongs to one Department.
  • FK property: Employee.DepartmentId. Navigations: Employee.Department and Department.Employees.
  • Conventions often discover the relationship from the navigation properties, principal key Department.Id and FK name DepartmentId.
  • Explicit Fluent API:
modelBuilder.Entity<Employee>()
    .HasOne(e => e.Department)
    .WithMany(d => d.Employees)
    .HasForeignKey(e => e.DepartmentId);
  • HasOne() specifies Employee's reference navigation; WithMany() specifies Department's collection; HasForeignKey() identifies the FK on the dependent.
  • After model changes, create and inspect a migration, then apply it. Invalid existing FK values can cause FK constraint creation to fail.

17. One-to-One Relationship

Employee ↔ PayrollAccount, FK uniqueness, shadow FKs and delete behavior.

  • One Employee has one PayrollAccount in the example; each PayrollAccount belongs to one Employee.
  • A common design has PayrollAccount.EmployeeId as FK to Employee.Id, with uniqueness enforcing at most one account per employee. An alternative is a shared primary key.
  • Navigation properties are reference properties: Employee.PayrollAccount and PayrollAccount.Employee.
  • Explicit configuration:
modelBuilder.Entity<Employee>()
    .HasOne(e => e.PayrollAccount)
    .WithOne(p => p.Employee)
    .HasForeignKey<PayrollAccount>(p => p.EmployeeId);
  • WithOne() configures the inverse reference; the generic type in HasForeignKey<PayrollAccount> identifies the dependent type.
  • Unique constraint/index: prevents multiple dependent records referencing the same employee. The FK also ensures the employee exists.
  • Shadow FK: EF Core model property not explicitly declared in the CLR entity. Can be useful but an explicit FK property is easier to access in application code.
  • Delete behavior: Cascade, Restrict/NoAction or SetNull should follow business and retention rules. SetNull requires a nullable FK.
  • Inspect migration for FK, uniqueness and delete behavior; duplicate or invalid existing values can prevent constraints from being applied.

18. Fluent API

ModelBuilder, OnModelCreating, chaining, property configuration and relationships.

  • ModelBuilder configures model metadata; override OnModelCreating(ModelBuilder modelBuilder) in the DbContext.
  • Entity<T>() selects an entity; Property() selects a property.
  • HasMaxLength() sets a maximum length; IsRequired() configures requiredness; HasColumnName() maps the database column name; HasColumnType() specifies database type; HasPrecision(precision, scale) configures suitable numeric precision and scale.
  • ToTable() configures table mapping; HasKey() configures keys; HasIndex() configures indexes.
  • Method chaining makes rules readable and centralizes database mapping.
  • Relationships use methods such as HasOne, WithMany, WithOne, HasForeignKey and OnDelete.
  • Model configuration can lead to migration changes; inspect generated migration and remember that not every model behavior change changes the database schema.
modelBuilder.Entity<Employee>()
    .Property(e => e.Email)
    .HasMaxLength(150)
    .IsRequired();

  • Deferred execution: LINQ query construction generally does not execute SQL until enumerated or a terminal operation runs.
  • Async: use await with asynchronous database APIs to avoid blocking threads while waiting for I/O; async does not guarantee one query is faster.

20. Repository Pattern

Data-access abstraction, interfaces, entity-specific repositories and request flow.

  • Repository Pattern places data-access logic behind a repository API rather than embedding queries in controllers.
  • Interface such as IEmployeeRepository defines available operations; implementation such as EmployeeRepository uses DbContext/DbSet and contains query logic.
  • Entity-specific repositories may exist for Employee and Department and add entity-specific queries.
  • Typical flow: Controller → Repository → DbContext → EF provider → PostgreSQL → result back to controller.
  • Benefits: separation of concerns, reuse, test substitution and a clearer boundary.
  • Trade-off: EF Core's DbContext/DbSet already provide repository-like behavior; a custom repository is optional and can add unnecessary abstraction if the application is simple.
  • Register repository interfaces and implementations with DI; repositories using scoped DbContext are commonly scoped too.
  • Repository handles data access, not HTTP concerns such as choosing status codes.

21. Unit of Work Pattern

Coordinating changes and committing them together.

  • Unit of Work coordinates pending changes across repositories for a business operation.
  • Example: add an Employee and PayrollAccount, then persist the related changes together.
  • Entity state management marks Added/Modified/Deleted; persistence sends changes to the database; coordination ensures the operation has a deliberate commit boundary.
  • EF Core's DbContext already provides Unit of Work-like behavior: it tracks changes and saves them with SaveChangesAsync().
  • A separate Unit of Work can expose repositories and one commit method, but it is an architectural choice rather than a requirement.
  • Repositories participating in one unit should generally share the same DbContext instance; otherwise their tracked changes cannot be committed by the same context save.
  • A single relational SaveChanges call normally uses a transaction when supported. Multiple SaveChanges calls are not automatically one shared transaction; use an explicit transaction if the entire multi-save workflow must be atomic.

22. Generic Repository Pattern

IGenericRepository<T>, GenericRepository<T>, constraints and entity-specific extensions.

  • Generic Repository reuses common CRUD operations instead of repeating the same code for Employee, Department and other entities.
  • IGenericRepository<T> defines operations; GenericRepository<T> implements them.
  • T is a type parameter: IGenericRepository<Employee> operates on employees; IGenericRepository<Department> operates on departments.
  • where T : class restricts T to reference types; the supplied type still needs to be part of EF Core's model to work as an entity.
  • DbSet<T> or context.Set<T>() accesses the EF entity set for T.
  • Entity-specific repositories can extend or compose the generic repository for custom queries, such as employees in a department.
  • Don't force specialized query behavior into generic CRUD methods when an entity-specific method is clearer.
  • With Unit of Work, repositories generally share a context and stage changes while the Unit of Work controls persistence.
public class GenericRepository<T> where T : class
{
    // Reusable operations use DbContext / DbSet<T>.
}

23. DTOs with EF Core APIs

Request/response DTOs, mapping, validation and overposting.

  • DTO: Data Transfer Object; defines data transferred across application boundaries, especially API requests/responses.
  • Entity: represents the EF Core model and is mapped to database structures. DTOs normally are not mapped to database tables.
  • Create DTO: input fields permitted for creation; typically excludes server-generated Id and internal fields.
  • Update DTO: fields the client is allowed to modify.
  • Response DTO: output fields the API chooses to expose, potentially including derived data such as DepartmentName.
  • Mapping: request DTO → entity for persistence; entity → response DTO for output. Mapping can be manual or use a library.
  • Benefits: controls exposed fields, reduces circular-reference serialization problems, allows API shape to evolve independently and supports request-specific validation.
  • Validation: attributes can include [Required], [MaxLength], [EmailAddress] and [Range]. With [ApiController], invalid model state commonly produces automatic 400 responses.
  • Overposting: do not blindly copy all request fields onto an entity. Explicitly control properties clients may change; authorization and server-side validation remain necessary.
  • GET usually returns response DTOs; POST accepts create DTO; PUT accepts update DTO; DELETE often uses an ID and may not need a DTO.

24. Loading Related Data

Eager loading, Include, ThenInclude, nested paths and performance.

  • Eager loading: request related entities as part of the query using Include() and ThenInclude().
  • Include(e => e.Department) loads Employee's Department navigation as part of the query.
  • ThenInclude(d => d.Employees) continues a path from an included Department to its Employees collection.
  • Use multiple Include calls for independent paths, such as Employee → Department and Employee → PayrollAccount.
  • EF Core often generates JOINs for eager loading, but exact SQL and whether one or multiple queries run depend on query shape/provider/settings.
  • Without loading, navigation properties may not be populated; lazy loading only works if configured and supported. A declared navigation does not itself load data.
  • DTO flow: query with needed relationships → map only needed fields → return DTO instead of the entire entity graph.
  • Performance: load only needed data; multiple collection includes can expand result sets; consider projections with Select and, where appropriate, AsSplitQuery(). Inspect generated SQL for complex queries.
var employees = await context.Employees
    .Include(e => e.Department)
    .Include(e => e.PayrollAccount)
    .ToListAsync();

25. InverseProperty Attribute

Resolving ambiguity when two entity types have multiple relationships.

  • [InverseProperty] is from System.ComponentModel.DataAnnotations.Schema.
  • It identifies which navigation property on the other entity is the inverse of the current navigation, helping EF Core pair properties correctly.
  • It is useful when two entity types have multiple relationships or several navigation properties of the same type make conventions ambiguous.
  • Its value is the inverse navigation property's name, not a database table or FK column name.
  • For simple unambiguous relationships, it is generally unnecessary.
  • Fluent API can configure the same complex relationships centrally in OnModelCreating(); choose a consistent approach.

26. Indexing in EF Core

Primary-key, unique, non-unique and composite indexes; performance trade-offs.

  • Index: database structure that can help locate rows efficiently; it does not replace the table or guarantee every query will be faster.
  • Primary-key index: supports unique identification; PK constraints are backed by suitable index structures in PostgreSQL.
  • Unique index: prevents duplicate indexed key combinations, e.g. unique Employee.Email if the business rule requires it.
  • Non-unique index: allows repeated values and can help filtering or joins, e.g. DepartmentId.
  • Composite index: indexes multiple columns in a defined order, e.g. (DepartmentId, Name). Column order affects which query patterns can use it effectively.
  • Indexes can help WHERE filters, JOINs and ORDER BY, depending on query plans, statistics and data distribution.
  • Foreign-key columns are not necessarily indexed automatically in every provider/model configuration; verify the model and migration.
  • Configure using HasIndex() and IsUnique(); inspect migration and apply it. Existing duplicate values can block a unique index.
  • Trade-offs: indexes use storage and must be maintained during inserts, updates and deletes. Too many indexes increase write overhead.
  • Create indexes based on query patterns, business constraints and query-plan evidence, not simply every column.
modelBuilder.Entity<Employee>()
    .HasIndex(e => e.Email)
    .IsUnique();

modelBuilder.Entity<Employee>()
    .HasIndex(e => new { e.DepartmentId, e.Name });

27. Enum Mapping

C# enum, database string conversion, JSON serialization and Swagger.

  • An enum defines a fixed set of named constants, e.g. EmployeeStatus.Active, Inactive, OnLeave.
  • EF Core normally stores an enum using its underlying numeric value unless configured otherwise.
  • .HasConversion<string>() configures EF Core to store/read enum names as strings in the database.
  • String storage is readable but uses more space; renaming enum members can require data migration, and invalid stored strings can fail conversion.
  • Database conversion vs JSON conversion: HasConversion<string>() controls database representation; JsonStringEnumConverter controls System.Text.Json serialization. They are separate.
  • Configure JSON serialization if API output should show "Active" instead of 0.
  • OpenAPI/Swagger schema should reflect string enum values when runtime serialization is configured that way; verify both schema and actual response.
  • Changing an existing integer column to string may require a data-conversion migration; don't assume a simple model configuration change safely converts existing values.

28. Serilog

Structured logging, levels, ASP.NET Core integration, sinks and management.

  • Logging: records events for startup, requests, successful operations, warnings, failures and exceptions.
  • Serilog: .NET logging library for structured events; it integrates with Microsoft's ILogger<T> abstraction when configured as a provider.
  • Levels: Verbose, Debug, Information, Warning, Error and Fatal. Microsoft levels map broadly: Verbose ≈ Trace; Fatal ≈ Critical.
  • Structured logging: use named placeholders, e.g. logger.LogInformation("Employee {EmployeeId} retrieved", employeeId), so EmployeeId is stored as a property rather than only embedded in text.
  • Sinks: destinations such as console, file, database or centralized logging service.
  • Integration: install compatible packages, configure Serilog as provider and choose levels/destinations; inject ILogger into controllers/repositories/services.
  • Log management: filter minimum levels, set retention, rotate files, centralize logs where useful and monitor recurring errors.
  • Security: never log passwords, tokens, connection strings or unnecessary sensitive employee data. Avoid duplicate exception logs without added context.

29. Database First & Scaffolding

Reverse engineering PostgreSQL into entities and DbContext.

  • Database First: start from an existing schema and generate C# entity classes and DbContext.
  • Scaffolding/reverse engineering: EF Core reads database metadata and generates entity classes, context and mapping configuration.
  • Table → class; column → property; database type → C# type.** Primary keys, foreign keys, constraints, nullability and relationships inform generated mappings.
  • Generated context typically contains DbSet properties and OnModelCreating() mappings.
  • Packages/tools: EF Core runtime, design package/tool, Npgsql provider and compatible versions. dotnet ef CLI is used from a terminal.
  • General command shape: dotnet ef dbcontext scaffold "<connection-string>" Npgsql.EntityFrameworkCore.PostgreSQL.
  • Useful options: --context, --output-dir, --context-dir, --table, --schema, --use-database-names, --no-onconfiguring.
  • OnConfiguring: scaffold may include provider/connection configuration. In ASP.NET Core, prefer configuration and DI via AddDbContext; --no-onconfiguring avoids generating that method configuration. Context must still be configured by the app.
  • Protect credentials; avoid placing production connection strings in source or shell history.
  • Database First vs Code First: Database First scaffolds from schema; Code First defines model and uses migrations to evolve schema.

30. Schema Changes & Re-scaffolding

Adding columns, --force, generated vs custom code and partial classes.

  • In Database First, update the database schema first when the database is the source of truth, then re-scaffold the model to reflect the schema.
  • Example: add PhoneNumber to PostgreSQL Student table; re-scaffolding can generate a matching Student property and updated mappings.
  • --force allows scaffolded files to be overwritten. It does not intelligently merge manual edits; existing generated files may be replaced.
  • Keep generated entities/context separate from custom services, controllers, DTOs, business rules and mapping logic.
  • Partial classes: if the generated entity is declared partial, add custom methods/properties in a separate partial class file that won't be overwritten by re-scaffolding.
  • A custom property in a partial class does not automatically map to a database column; persistent mapping must be configured appropriately.
  • Re-scaffolding reads the database; it does not create the database column. Only selected tables/schemas are regenerated when those options are used.
  • Safe workflow: verify schema → commit/save changes → scaffold with correct selection/options → review source-control diff → build/test → verify read/write behavior.
Remember: --force is an overwrite option, not a merge option. Protect custom work before using it.
