Part 1 — REST API & HTTP Concepts

Core fundamentals REST is an architectural style for networked applications. HTTP is the protocol commonly used to communicate with REST APIs. ASP.NET Core is the framework used to build the API.

1.1 REST architecture

A client sends an HTTP request to a resource-oriented endpoint. The API processes it and returns an HTTP response, often containing a JSON representation of the resource.

Client application (browser / frontend)
↓ HTTP request
ASP.NET Core API → routing → controller/action
↓ process request
HTTP response: status code + headers + optional body

1.2 REST architectural constraints

ConstraintMeaningWhy it matters
Client–ServerClient interface and server data/processing concerns are separated.They can evolve independently if the API contract remains compatible.
StatelessnessEach request carries the information needed to process it; the server does not depend on conversational state retained from earlier requests.Improves scalability and makes requests easier to route across server instances.
CacheabilityResponses identify whether and how they may be cached.Can reduce latency and repeated work.
Uniform InterfaceResources are identified consistently; representations and self-descriptive messages are used, with hypermedia as a REST constraint.Creates a predictable interface.
Layered SystemRequests may pass through gateways, proxies, load balancers or middleware.Supports separation of responsibilities and infrastructure scaling.
Code on Demand (optional)A server may send executable code, such as JavaScript, to a client.Extends client behavior; this constraint is optional.
Exam trap: Stateless does not mean the API cannot use a database, cache data or authenticate users. It means the server does not rely on stored conversational context from a prior request to understand the current request.

1.3 Resources, endpoints and representations

  • Resource: The conceptual item being managed, such as a student.
  • Resource identifier: A URI identifying a resource, for example /api/students/5.
  • Endpoint: Commonly, a route plus an HTTP method that exposes an operation.
  • Representation: A transferable form of resource data, often JSON or XML.
ExampleMeaning
GET /api/studentsRetrieve the collection.
GET /api/students/5Retrieve one student.
application/jsonMedia type of a JSON representation.

1.4 RESTful API design principles

  • Use resource-oriented nouns in URLs: /api/students, not command-heavy names such as /api/getStudents.
  • Use HTTP methods according to their semantics.
  • Return meaningful status codes and consistent response structures.
  • Use appropriate headers and media types.
  • Support filtering, sorting and pagination for large collections when required.
  • Consider compatibility before changing public request or response contracts.
  • Do not expose internal database or implementation details unnecessarily.

1.5 HATEOAS

HATEOAS means Hypermedia as the Engine of Application State. A response can contain links that tell clients which related resources or transitions are available.

{
  "id": 5,
  "name": "Harshitha",
  "_links": {
    "self": "/api/students/5",
    "collection": "/api/students"
  }
}

Links can help clients navigate without hardcoding every related URI. A links object alone is not necessarily a complete HATEOAS implementation; links should represent meaningful navigation or actions. HATEOAS is part of REST's uniform-interface constraint, although many practical APIs do not fully implement it.

1.6 HTTP requests and responses

A request includes a method, target/URL, headers and possibly a body. A response includes a status code, headers and possibly a body.

POST /api/students HTTP/1.1
Content-Type: application/json
Accept: application/json

{
  "name": "Harshitha",
  "age": 22,
  "grade": "A"
}
HTTP/1.1 201 Created
Content-Type: application/json
Location: /api/students/5

{
  "id": 5,
  "name": "Harshitha",
  "age": 22,
  "grade": "A"
}

1.7 HTTP methods

MethodTypical purposeImportant note
GETRetrieve a representation.Safe and idempotent by definition of intended semantics.
POSTSubmit data for processing; often create a resource.Not generally idempotent.
PUTCreate or replace the target resource's state, depending on API semantics.Idempotent; not safe.
PATCHApply a partial modification.May or may not be idempotent depending on the patch operation.
DELETERequest removal of a resource.Idempotent in intended effect, even if repeated response codes differ.

ASP.NET Core input formatters deserialize supported request formats into .NET objects. Content negotiation helps choose an appropriate response representation. It is distinct from model validation.

1.9 HTTP status codes

RangeClassExamples
100–199InformationalRequest processing information.
200–299Success200 OK, 201 Created, 204 No Content.

400–499Client/request error400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed, 409 Conflict.

1.10 Safe vs idempotent methods

MethodSafe?Idempotent?
GETYesYes
POSTNoGenerally no
PUTNoYes
PATCHNoDepends on the operation
DELETENoYes

Safe means the requested operation is intended to be read-only. Idempotent means repeating the same request has the same intended effect on server state as making it once. DELETE may return 204 the first time and 404 the second time while remaining idempotent.

1.11 HTTPS

HTTPS is HTTP protected by TLS. TLS provides confidentiality, integrity and server authentication through certificate validation. HTTPS does not replace application authentication, authorization, validation or secure design.

Part 2 — API Routing

Routing matches an incoming HTTP request to an endpoint. In controller-based ASP.NET Core APIs, routes and HTTP method attributes help determine which controller action can handle the request.

2.1 Routing and route templates

A route template is a pattern used to match a URL path. For example, api/students/{id} contains a route parameter named id.

2.2 Attribute routing: [Route] and [controller]

[ApiController]
[Route("api/[controller]")]
public class StudentsController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult GetStudent(int id) { ... }
}

[Route] defines a route template. The [controller] token is replaced with the controller name without the Controller suffix; StudentsController therefore maps to students. The example action matches a GET request such as /api/students/5.

2.3 Route parameters vs query parameters

TypeExampleCommon use
Route parameter/api/students/5Identify a particular resource.
Query parameter/api/students?grade=AFilter, sort, search or paginate a collection.

Route constraints can restrict matches, for example {id:int}. A route constraint helps select a route; it is not a substitute for business validation.

2.4 Endpoint routing and endpoint registration

  • builder.Services.AddControllers() registers controller-related services.
  • app.MapControllers() maps attribute-routed controller endpoints.
  • These are different operations: registering services does not itself map the endpoints.
  • Endpoint routing matches a request to a registered endpoint based on route and other metadata, including HTTP method.

2.5 Controller and action selection

Controller discovery makes controller types available to the MVC framework. Routing and endpoint metadata determine which action can handle a request. Action selection considers the route, HTTP method and applicable constraints/metadata.

AttributePurpose
[HttpGet]Maps GET requests.
[HttpPost]Maps POST requests.
[HttpPut]Maps PUT requests.
[HttpPatch]Maps PATCH requests.
[HttpDelete]Maps DELETE requests.

2.6 Routing flow

Incoming HTTP request
↓
Endpoint matching: route + method + metadata
↓
Controller and action selection
↓
Action method execution
↓
HTTP response
Status-code distinction: No matching route commonly results in 404. If a resource path exists but the HTTP method is unsupported, the response commonly is 405. Exact behavior can depend on routing and endpoint configuration.

2.7 Routing interview points

  • Attribute routing places route definitions on controllers/actions.
  • The same route path can support different HTTP methods.
  • Route values are commonly bound from the path; query values are commonly bound from the query string.
  • Endpoint registration and service registration are separate steps.
  • Routing identifies an endpoint; model binding and validation then process the action inputs.

Part 3 — API Validation

3.1 Validation fundamentals and why validation is required

Validation checks whether incoming data meets structural, data and application rules. It prevents invalid data from being processed or stored and gives clients actionable feedback.

3.2 Client-side vs server-side validation

Client-sideServer-side
Runs in the frontend; improves usability and gives quick feedback.Runs in the API; is essential because clients can bypass frontend checks.
Not a security boundary.Must enforce important data and business rules.

3.3 Data, model and business validation

  • Data validation: Checks values, format, lengths and ranges.
  • Model validation: Checks a bound model against configured validation rules.
  • Business validation: Checks whether an operation is allowed under application rules, such as whether a unique student identifier already exists.

A request can pass model validation and still fail a business rule.

3.4 ASP.NET Core validation pipeline

Incoming HTTP request
↓
Request-body deserialization and model binding
↓
Model validation and ModelState errors
↓
With [ApiController]: automatic 400 for invalid model state by default
↓
Action runs if validation passes

Without automatic API-controller behavior, an action commonly checks ModelState.IsValid explicitly. The exact behavior can be customized.

3.5 Data Annotation validation attributes

AttributePurpose / exampleImportant note
[Required]Requires a value.Behavior depends on the property's type; non-nullable value types already have a default value unless additional rules are used.
[Range(1, 120)]Restricts a numeric value to a range.It does not check every business rule.
[StringLength(100)]Sets a string length limit.Can specify a minimum and maximum length.
[MinLength(3)]Requires a minimum length.Does not alone make a value required.
[MaxLength(50)]Sets a maximum length.Useful for strings and collections.
[RegularExpression("...")]Checks a value against a pattern.Pattern must match the intended format.

3.6 Automatic validation with [ApiController]

[ApiController] enables API-specific behaviors including automatic HTTP 400 responses when model validation fails, binding-source inference and a requirement for attribute routing. Automatic invalid-model responses commonly use ValidationProblemDetails, which can contain field-level errors.

3.7 Invalid requests and appropriate validation responses

ScenarioTypical response
Required name missing or age outside allowed range400 Bad Request
Business rule violationOften 400 or 409, depending on the rule and API contract.
Student ID does not exist404 Not Found
Unexpected server failure500 Internal Server Error

Validation responses should be consistent and useful, but should not disclose sensitive internal details.

3.8 Validation interview points

  • ModelState.IsValid indicates whether model binding and validation have reported errors in model state.
  • [ApiController] usually rejects invalid model state before the action runs.
  • Client-side validation is not a replacement for server-side validation.
  • Data annotations do not replace database constraints or application-specific business checks.

Part 4 — API Error Responses & Exception Handling

4.1 Error handling and its purpose

Error handling detects, manages and communicates failures. Centralized exception handling reduces duplicated try/catch logic, standardizes error responses, supports logging and avoids exposing internal details.

4.2 HTTP errors: 400, 404 and 500

StatusMeaningExample
400 Bad RequestThe request is invalid.Model validation fails.
404 Not FoundThe requested resource or endpoint cannot be found.Student ID does not exist.
500 Internal Server ErrorAn unexpected server failure occurred.An unhandled exception.

An error response is an HTTP result; an exception is an exceptional condition represented in application code. A missing student can be handled normally without throwing an exception.

4.3 Consistent error responses and ProblemDetails

ASP.NET Core supports the ProblemDetails format for HTTP API errors and ValidationProblemDetails for validation errors.

{
  "type": "https://example.com/errors/invalid-request",
  "title": "Bad Request",
  "status": 400,
  "detail": "The submitted student data is invalid."
}
  • type: identifier for the problem type.
  • title: short summary.
  • status: HTTP status code.
  • detail: occurrence-specific explanation.

Additional fields such as a trace identifier may be included. Never expose stack traces, secrets, credentials or internal file paths in production responses.

4.4 Global exception handling and centralized processing

Global exception handling catches otherwise unhandled exceptions from downstream parts of the HTTP request pipeline and turns them into a controlled response where possible.

Request enters pipeline
↓
Downstream code throws an exception
↓
Exception-handling middleware invokes registered handler
↓
Log exception and map to suitable response
↓
Client receives consistent error response

4.5 IExceptionHandler

IExceptionHandler is a framework interface for implementing exception-handling logic in modern ASP.NET Core, including .NET 8 and later. It defines TryHandleAsync(HttpContext, Exception, CancellationToken).

  • Inspect the exception and HTTP context.
  • Log appropriate details.
  • Choose a suitable response status and body.
  • Return true if the exception was handled, or false if this handler did not handle it.

4.6 Registering and integrating the handler

ConfigurationResponsibility
builder.Services.AddExceptionHandler<THandler>()Registers the handler type with dependency injection.
app.UseExceptionHandler()Adds exception-handling middleware to the HTTP pipeline.

Registering the handler alone does not enable global handling; the middleware must be configured. Place it early enough to catch exceptions from downstream middleware and endpoint execution. A response that has already started may not be replaceable.

4.7 Mapping exceptions to HTTP responses

Known conditionPossible mapping
Known student-not-found exception404 Not Found
Business-rule conflict409 Conflict
Unexpected exception500 Internal Server Error

Do not map every exception to 400. The response should reflect whether the issue is a client error, known domain condition or unexpected server failure.

4.8 Custom exception middleware vs IExceptionHandler

Custom middlewareIExceptionHandler approach
You implement and maintain the middleware's exception-handling logic.You implement the framework handler interface and use ASP.NET Core's exception middleware.
Must be registered in the pipeline.Handler is registered with AddExceptionHandler; middleware is enabled with UseExceptionHandler.
Can centralize exceptions.Also centralizes exception processing while using a framework abstraction.

IExceptionHandler is not middleware by itself; it is a handler abstraction used by exception-handling middleware.

4.9 Consistent exception handling checklist

  • Return an appropriate status code and consistent error format.
  • Log enough detail for diagnosis without leaking sensitive information to clients.
  • Include a trace identifier when useful.
  • Do not silently ignore exceptions.
  • Avoid attempting to write multiple responses for the same request.
  • Distinguish expected results (such as not found) from unexpected exceptions.

4.10 Student Management System application goals

Part 5 — Swagger & OpenAPI

5.1 OpenAPI fundamentals and specification

OpenAPI is a specification for describing HTTP APIs in a standardized, machine-readable document. It explains the API contract without requiring consumers to read implementation code.

  • Documents paths, HTTP operations, parameters, request bodies and responses.
  • Describes schemas and reusable components.
  • Supports documentation tools, testing, and client-code generation.
  • An OpenAPI document can be represented as JSON or YAML.

5.2 Swagger vs OpenAPI

OpenAPISwagger
The specification/standard describing the API.A family of tools for working with API descriptions.
Defines document structure and meaning.Tools can generate, edit, display or interact with API documentation.

5.3 Swagger ecosystem and architecture

ComponentRole
Swagger / OpenAPI GeneratorProduces an OpenAPI document from discovered API descriptions and metadata; exact generator depends on packages.
Swagger UIRenders the document as interactive web documentation.
API ExplorerExposes descriptions of discovered API actions and endpoints for tooling.
ReflectionLets .NET tooling inspect types, methods, properties and attributes.
OpenAPI JSONMachine-readable description consumed by UI and other tools.

5.4 API discovery: controller and action discovery

Documentation tooling discovers API endpoints and their metadata, including controller actions, route templates, HTTP methods, parameters, request-body types, response types, status codes and schema information.

5.5 API Explorer

API Explorer exposes descriptions of discovered actions and endpoints. It helps documentation tooling understand routes, methods, parameters and response metadata. It does not itself render Swagger UI or necessarily generate the final OpenAPI document.

5.6 Reflection and metadata

Reflection allows .NET code to inspect types, methods, properties and attributes at runtime. API tooling can use reflection along with endpoint metadata and API Explorer descriptions to understand an action's route, HTTP method and model types.

5.7 Complete OpenAPI generation flow

Controllers
↓
Action methods and endpoint metadata
↓
API Explorer descriptions
↓
Metadata / reflection
↓
Swagger / OpenAPI generator
↓
OpenAPI document
↓
OpenAPI JSON endpoint

Exact internals differ by ASP.NET Core version and documentation packages. The important idea is that the generator builds a standardized description from API metadata.

5.8 OpenAPI JSON and /openapi/v1.json

A configured ASP.NET Core OpenAPI endpoint may expose a document at /openapi/v1.json. This path is not universal; it depends on application configuration.

OpenAPI fieldWhat it describes
pathsAPI paths and operations.
parametersRoute, query, header or other parameters.
requestBodyExpected request body and media types.
responsesPossible HTTP responses and schemas.
components/schemasReusable data schemas.

5.9 Generator vs UI

  • The generator produces the OpenAPI document.
  • The JSON endpoint serves the document.
  • Swagger UI loads the document and displays it interactively.
  • Swagger UI does not directly call controller methods; when testing, it sends HTTP requests through the normal API pipeline.

Part 6 — Swagger UI

6.1 Fundamentals and purpose

Swagger UI is a browser-based interface that displays an OpenAPI document and lets developers explore endpoints and send test requests.

6.2 Reading documentation and viewing endpoints

Each operation usually shows its HTTP method, path, description, parameters, request-body schema and documented responses. The actual list depends on the generated document and application configuration.

6.3 Parameters and request bodies

InputExamplePurpose
Path parameter/api/students/5Identifies a resource.
Query parameter?grade=AFilters or changes the query.
HeaderAuthorization tokenSupplies request metadata or credentials.
Request bodyJSON student dataSubmits structured content.

A schema describes property names, types, constraints and sometimes required fields. Displayed schema details depend on API metadata and OpenAPI generator support.

6.4 Executing an API through Swagger UI

  1. Select an endpoint.
  2. Choose Try it out when available.
  3. Enter path/query parameters, headers or request body.
  4. Select Execute.
  5. Inspect the response status, body, headers and request details.
Careful: Swagger UI sends real HTTP requests. POST, PUT, PATCH and DELETE operations may change data. Use test data and understand the environment before executing them.

6.5 Understanding responses and status codes

CodeMeaning
200Success with a response representation in common scenarios.
201Resource created.
204Success without a response body.
400Invalid request.
404Resource or endpoint not found.
500Unexpected server error.

6.6 Swagger request flow

6.7 Swagger UI vs OpenAPI JSON

OpenAPI JSON is the machine-readable API description; Swagger UI is the human-friendly interface that renders it and can issue requests. Swagger UI does not replace server-side validation, authentication or authorization.

Part 7 — XML Documentation

7.1 XML documentation comments and ///

C# XML documentation comments start with /// immediately above the code element they describe. Ordinary comments such as // are not emitted as XML documentation.

/// <summary>
/// Represents a student in the system.
/// </summary>
public class Student
{
    /// <summary>
    /// Gets or sets the student's identifier.
/// </summary>
    public int Id { get; set; }
}

7.2 Required and useful XML tags

TagPurpose
<summary>Brief description of a type or member.
<param name="...">Describes a method parameter.
<returns>Describes a method's return value; not needed for void methods.
<exception cref="...">Documents an exception and when it may occur.
<remarks>Additional details.
<example>Example usage.
<see cref="...">Reference to another code element.
<typeparam name="...">Documents a generic type parameter.
<value>Describes a property's value.

7.3 Documenting classes and methods

Use <summary> to describe the responsibility of a class or the purpose of a method. Keep the comment accurate and focused on what the code actually does.

7.4 Parameters, return values and exceptions

/// <summary>
/// Divides two numbers.
/// </summary>
/// <param name="a">The numerator.</param>
/// <param name="b">The denominator.</param>
/// <returns>The division result.</returns>
/// <exception cref="DivideByZeroException">
/// Thrown when the denominator is zero.
/// </exception>
public double Divide(double a, double b)
{
    return a / b;
}

Documentation describes possible behavior; it does not itself enforce validation or guarantee that an exception is thrown in every runtime context.

7.5 Documenting models and properties

Document model classes and public properties so developers understand the purpose and meaning of each field. The <summary> tag is common for both classes and properties; <value> can describe a property's value specifically.

7.6 Documenting enums and enum members

/// <summary>
/// Represents a student's enrollment status.
/// </summary>
public enum StudentStatus
{
    /// <summary>The student is enrolled.</summary>
    Active,
    /// <summary>The student is not enrolled.</summary>
    Inactive
}

7.7 Common XML documentation mistakes

  • Using // instead of ///.
  • Leaving out a method's parameter descriptions.
  • Using <returns> for a void method.
  • Writing comments that no longer match the implementation.
  • Assuming comments automatically appear in Swagger without generating and integrating the XML file.
  • Documenting exceptions inaccurately.

Part 8 — XML Documentation with Swagger

8.1 Enabling XML documentation generation

The project file (.csproj) can enable XML documentation generation using the GenerateDocumentationFile property.

<PropertyGroup>
  <GenerateDocumentationFile>true</GenerateDocumentationFile>
</PropertyGroup>

During compilation, the compiler emits an XML file containing eligible documentation comments, commonly alongside the compiled assembly in the build output directory.

8.2 Generated XML file vs OpenAPI JSON

The OpenAPI generator must be configured to read the generated XML file. The exact configuration depends on the tooling and ASP.NET Core version. Part 9 — API Versioning

9.1 Versioning fundamentals and why APIs need versions

API versioning allows a public API contract to evolve while existing clients continue using a supported earlier contract. It helps manage breaking changes, migration and client compatibility.

9.2 Breaking vs non-breaking changes

ChangeTypical classification
Add an optional response property.Usually non-breaking, though strict clients can be affected.
Remove a response property.Breaking for clients that rely on it.
Rename a property or change its type.Typically breaking.
Add a new independent endpoint.Usually non-breaking.
Make an optional request field mandatory.Breaking for clients that omit it.

Classification depends on the exact contract and client behavior; additive changes are not guaranteed to be harmless to every client.

9.3 Backward compatibility and multiple versions

Backward compatibility means the API continues to support clients relying on the older contract. An API may expose v1 and v2 at the same time, allowing clients to migrate on their own schedule.

9.4 Four versioning strategies

StrategyExampleTrade-off
URL-based/api/v1/studentsVisible and easy to route; version appears in the URL.
Query-string/api/students?api-version=1.0Easy to add to a request; version is a query parameter.
Header-basedapi-version: 1.0Keeps version out of the URL; clients must send the header.
Media-typeAccept: application/json;v=1.0Version is tied to the representation/media-type convention.

These are illustrative conventions. The exact parameter name, header and media-type syntax depend on the versioning library and configuration.

9.5 Version selection and versioned endpoints

Version selection determines which API version handles the request. Depending on the configured strategy, the version is read from the URL, query string, header or media type. Versioned endpoint metadata associates operations with the versions they support.

9.6 Supporting multiple versions and client compatibility

  • Keep old and new contracts available when required.
  • Document differences between versions.
  • Give clients time to migrate.
  • Avoid silently changing the meaning of an existing field or operation.
  • Define behavior for unsupported or missing versions.

9.7 API version lifecycle

Design and introduce a version
↓
Release and support clients
↓
Introduce newer version if needed
↓
Deprecate older version and communicate timeline
↓
Retire older version according to policy

Deprecation signals that a version is planned to be phased out; it does not necessarily mean it stops working immediately. Retirement is the point when support ends.

9.8 ASP.NET Core versioning concepts

Adding /v1 to a URL alone does not configure a complete versioning system. A version-aware implementation typically configures version selection and associates endpoint/controller actions with supported versions, often using an API versioning package. API versioning is distinct from the deployed application's software version.

TermShort definition
RESTArchitectural style for networked systems.
HTTPRequest/response protocol used by web APIs.
ResourceConceptual item exposed by an API.
EndpointRoute/method combination that exposes an operation.
HATEOASHypermedia as the Engine of Application State.
IdempotentRepeating a request has the same intended effect on server state.
RoutingMatching requests to endpoints.
Model bindingMaps request data to action parameters or model objects.
Model validationChecks bound model data against validation rules.
Business validationChecks domain-specific rules.
ProblemDetailsStandardized shape for describing an HTTP API problem.
IExceptionHandlerASP.NET Core interface for centralized exception handling.
OpenAPISpecification for describing HTTP APIs.
Swagger UIInteractive interface that renders an OpenAPI document.
API ExplorerExposes API action descriptions to tooling.
Reflection.NET ability to inspect types and members at runtime.
XML documentationStructured C# comments that can be emitted into an XML file.
Backward compatibilityContinued support for clients using an earlier contract.
